Follow a request

About 10 minutes. Mission link: trace a request from browser to server and say where it can fail or be attacked.

Your win today: given a symptom (an error code, a missing site, a tampered page), name the step of the request journey where it happened, and the protection that guards the risky steps.

The journey in four steps

When you type a web address into the browser, MDN says these steps happen:

  1. Address lookup. The browser asks a DNS server for the real address of the server the site lives on.
  2. Request. The browser sends an HTTP request asking for a copy of the site. This message, and all other data between client and server, travels over TCP/IP.
  3. Response. If the server approves, it replies "200 OK" and sends the site's files as a series of small chunks called packets.
  4. Assembly. The browser puts the chunks together into a complete page.

Source: MDN, How the web works.

Where each step can fail

SymptomStepWhy
Browser can't find the site at all1. Address lookupThe browser needs the IP address from DNS before it can retrieve the website.
Some data is lost on the way2–3. TCP/IP transportPackets are sometimes dropped or corrupted; the client can ask for just the missing ones.
Error code such as 403, 404 or 5033. ResponseThe server answered, but not with the page. 403: access refused. 404: not found. 503: temporarily unable to handle it.

Source: MDN, as above.

Where it can be attacked: TLS

MDN describes HTTPS as a secure version of HTTP that stops bad people from reading your data while it is being transported. The book High Performance Browser Networking breaks the protection down. The TLS protocol is designed to provide three services:

  • Encryption: obfuscates what is sent between hosts.
  • Authentication: lets the browser verify the server is who it claims to be, not someone pretending to be it by spoofing its name or IP address.
  • Integrity: detects tampering and forgery of messages.

Source: HPBN, Transport Layer Security (TLS).

Security lens: each service answers a different attack. Reading traffic is stopped by encryption. Impersonating a site is stopped by authentication. Changing traffic is stopped by integrity.

Try it on your own machine

Run this in a terminal (macOS and Linux have curl; Windows 10+ has it too):

curl -sI https://developer.mozilla.org/en-US/

The -I flag asks for just the headers. Find the status line (it should say HTTP/2 200) and compare it with the example response in the MDN article. Then request a page that does not exist and read the code:

curl -sI https://developer.mozilla.org/en-US/no-such-page-xyz

I ran both while preparing this lesson and got 200 for the first and 404 for the second. Which step of the journey does the code come from?
